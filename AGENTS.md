# Инструкция ИИ для проекта Warcraft TD

Этот файл определяет только порядок работы ИИ. Сведения об игре здесь не хранятся.

## Перед каждой задачей

1. Прочитать `STATE.md`.
2. Прочитать `outputs/Warcraft_TD_Project_Index.md`.
3. По индексу открыть только профильные источники задачи.
4. Перед изменением кода прочитать описание затронутых модулей и их контрактов в `outputs/Warcraft_TD_Modules.md`.
5. Проверить реальные файлы: документация описывает намерение, но не гарантирует состояние реализации.

## Иерархия истины

При конфликте использовать порядок:

1. последнее прямое указание пользователя;
2. профильный источник из индекса;
3. модульные контракты;
4. `STATE.md`;
5. текущее поведение кода.

Код прототипа не является доказательством утверждённого игрового правила.

## Выполнение задачи

- Выполнять прямой запрос полностью и самостоятельно, пока не требуется новое решение пользователя.
- Не превращать предположение в утверждённое правило. Временное решение явно помечать.
- Каждую новую сущность или механику закреплять за одним модулем-владельцем.
- Не дублировать формулы, состояние или бизнес-правила в нескольких модулях.
- Связывать модули через описанный контракт, интерфейс, команду или событие.
- Не расширять монолит, если функция уже относится к отдельному модулю.
- Не менять несвязанные пользовательские файлы и не удалять данные без прямого запроса.

## Git

- Перед изменениями проверять `git status` и сохранять несвязанные изменения пользователя.
- Работать небольшими логическими изменениями; одна завершённая задача — один понятный коммит.
- Не добавлять Unity `Library`, `Temp`, сборки, логи и локальные настройки.
- Не коммитить код с проваленной обязательной проверкой.
- Не переписывать историю, не выполнять force-push и не удалять ветки/теги без прямого запроса.
- После успешной проверки фиксировать задачу коммитом, если пользователь не запретил коммит для этой задачи.
- Для крупных независимых направлений использовать ветки `feature/...`, для исправлений — `fix/...`, для документов — `docs/...`.

## Документация

- Новое продуктовое решение записывать в `Overview`.
- Новое правило игрового процесса записывать в `Design`.
- Новый сюжетный факт записывать в `Story`.
- Новый технический подход или этап записывать в `Development`.
- Новую зависимость, ответственность или контракт записывать в `Modules`.
- Не копировать одно подробное правило в несколько источников: вместо этого давать ссылку.

## Проверка и завершение

1. Выполнить проверки, установленные в `Warcraft_TD_Development.md` для затронутого типа изменения.
2. Обновить профильные источники и статус соответствующих модулей.
3. Обновить `STATE.md`: результат, изменённые файлы, проверки, блокеры и следующий шаг.
4. Зафиксировать проверенное логическое изменение в Git и указать хеш коммита в `STATE.md`.
5. Сообщить пользователю фактический результат и незавершённые ограничения.
6. Не задавать вопрос автоматически, если безопасное продолжение уже определено документами.
